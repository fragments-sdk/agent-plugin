Help the person fill missing page examples with their configured coding agent. One concrete page represents each route pattern; other records must not add boards.

If `page_coverage` and `page_example` are available, read coverage first. Use its returned scope unchanged, and investigate only patterns marked eligible: never attempted, or eligible again because the source changed. If the person explicitly asks to recheck previously explained gaps because app data, access or setup may have changed, include those missing patterns too. Keep healthy examples and existing choices. Otherwise retain previously explained gaps. Work through at most 20 patterns, 40 tool calls and five minutes in one pass; batch source reads and stop when no supported example remains.

Inside Fragments, this workflow is already in the turn's instructions; do not load it again through a Skill tool or an external skill path. Use `pages` with `picture: false` to find known pages, their source files and links, then use `read_file` with project-relative paths as the primary way to inspect the repository. If that tool is deferred, find Fragments' `read_file` through the host's tool search. Follow imports from those files to the router, navigation and relevant screen or loader. Use `look` with a real `path` and, when needed, source-verified navigation `steps` for current runtime evidence. These built-in page and source tools are sufficient for the investigation; shell access, a separate browser and Computer tools are optional. Their absence is not a reason to skip the available `read_file` investigation or request broader permissions. Respect any actual restriction on a file or operation.

Trace the missing patterns through the project's router, navigation, loaders and existing fixtures. Prefer a real page already visited or an actual destination exposed by the running app. Use approved browser or Computer tools when available to open existing records through ordinary navigation. Buttons can navigate without an `href`; inspect their source before using an ambiguous control. Do not execute arbitrary event handlers to extract their destinations. A fixture is useful only when the current app actually serves it. Never guess IDs, borrow unrelated resource IDs, fabricate tokens or chart payloads, enumerate records through APIs, or inspect credentials or auth storage.

Inside Fragments, call `page_example` once for each resolved pattern with the returned `scope`, its `family`, and the real concrete `route`. The tool validates and retains the example and queues the existing capture pipeline; registration or a queued capture is not a successful picture. Let Fragments handle related patterns through its shared planner. Do not create another route planner or write example state files yourself.

When an eligible pattern cannot be resolved, register its outcome through `page_example` with the same `scope` and `family`, plus `unavailable: { reason, detail }`. Use the supported reason that the evidence establishes: `empty-data`, `sign-in`, `invitation`, `special-context` or `not-found`. Keep `detail` concise, no more than 300 characters, and name the actual missing prerequisite. An empty list, a permission redirect and an invalid candidate are different outcomes. Do not label an unexplored pattern unavailable merely because the pass reached its limit.

Source may establish that a pattern requires a real invitation link or generated export payload. After checking known links/visits and relevant source, if no usable example was observed, record `invitation` or `special-context` with detail naming the prerequisite and saying that no example was observed in this pass; do not claim none exists. Runtime verification is not required to remember that source-established prerequisite. `sign-in`, `empty-data` and `not-found` require actual runtime evidence. A loading or failed `look` is inconclusive for those states; it does not invalidate independent source evidence. If neither source nor runtime establishes an outcome, leave the pattern eligible and report the limit.

After the pass, read `page_coverage` once more. Report the actual pictured, queued, failed and unresolved results; queued pages remain pending. Summarize the prerequisites still needed and stop. Do not repeatedly retry terminal outcomes or ask the person to paste URLs that ordinary navigation can supply.

If the page tools are absent or Fragments is unavailable, continue only with available read-only source and browser evidence. Report source-verified candidate paths and exact unmet prerequisites; explain that they were not registered or pictured. Do not ask for manual MCP configuration, install another agent, change host settings or block normal static checks.

This workflow does not edit source or configuration, create records, submit forms, send invitations or change access to obtain a picture. Leave sign-in to the person on the app's own page. Keep representative addresses in Fragments' private page tools; do not print tokens, JWTs, credentials or record contents in logs, receipts or the final report.
